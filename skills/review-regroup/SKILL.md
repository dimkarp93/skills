# Подготовить ветку к ревью

Сначала прочитай `~/.claude/skills/commit-review-core/RULES.md`. Все скрипты — в
`~/.claude/skills/commit-review-core/scripts/`. Проект должен быть на Go.

Метод не деструктивный: исходная ветка и рабочая копия не трогаются. Новая история строится в
новой ветке `review/<ветка>` в отдельном worktree, поэтому бэкап-ветка, `git reset`, `git stash` и
перезапись файлов не нужны. Все шаги ниже — обычные небольшие вызовы; их можно выполнять и в
субагенте.

## Шаги

1. **Проверки.** Дерево чистое (`git status`), известна база (`rr-plan.sh base`, при сомнении
   спроси; `AskUserQuestion` недоступен, а пользователь назвал базу и команду сборки — используй
   их). Команда сборки: `go build -o /dev/null ./...`; если в корне нет `go.mod` —
   `cd <каталог модуля> && go build -o /dev/null ./...`.
2. **Черновик.** `rr-plan.sh plan <база>` даёт `--stat` и строки `[вид] текст (файл)` от
   `commitkind hint`. Определи фичи ветки (имена — короткие теги `[0-9a-z-]`), для новых Go-файлов
   возьми `commitkind funcs` и `commitkind order` (функции от простых к сложным). Расставь фичи
   от простых и независимых к сложным, зависимости раньше зависящих. Полные диффы не читай,
   только точечно там, где надо разделить логику.
3. **Обзор — согласовать.** Прежде чем строить файл плана, покажи пользователю компактный обзор
   (формат в RULES.md, раздел «Обзор для пользователя»): топ-5 самых важных фич (топ-3, если
   топ-5 слишком сложно) в порядке выполнения с 1–3 главными функциями каждой, остальные фичи
   одной строкой, порядок «от простых к сложным» и зависимости. **Жди согласия** на фичи, порядок
   и основные функции, правь по замечаниям. Детальный план на десятки коммитов согласовывать не
   нужно.
4. **Файл плана.** Запиши его инструментом записи файла (не через shell) в scratchpad или
   `/tmp`, формат ниже. Порядок: фичи строго по очереди (технические коммиты остаются внутри
   своей фичи и идут перед логикой), внутри фичи функции от простых к сложным, тема каждого
   коммита `[фича] [вид] текст`, реализации логики — вид `logic`. Промежуточные версии файлов
   берутся из коммитов исходной ветки (`git log --oneline <база>..HEAD`, `git show <rev>:путь`
   для чтения).
5. **Исполнение.** Один вызов: `rr-regroup.sh <файл плана>`. Скрипт создаёт worktree и ветку
   `review/<ветка>`, для каждого шага кладёт нужные файлы, собирает проект, коммитит через хуки,
   проверяет тему, а в конце сравнивает итоговое дерево с исходной веткой, запускает
   `commitkind check` (формат, класс, непрерывность фич) и печатает обзор фич. Ошибка на шаге —
   скрипт останавливается, оставляет worktree и печатает, как его убрать; поправь план и запусти
   заново с другим `branch NAME`.
6. **Отчёт.** Начни с обзора (`commitkind overview` уже напечатан скриптом): фичи по порядку и
   топ-5 самых важных, затем таблица коммитов новой ветки и результат сравнения деревьев.
   Подменять исходную ветку скилл не должен: скажи, как это сделать (например
   `git branch -f <ветка> review/<ветка>` или переключиться на новую), и оставь решение
   пользователю. Force-push не делай.

## Формат файла плана

```
base 743bb58
source HEAD
build cd skills/x/mod && go build -o /dev/null ./...
branch review/my-feature
step [checker] [chore] add go.mod
file - skills/x/mod/go.mod
step [checker] [add] add commitkind checker skeleton
body optional second paragraph of the message
file - skills/x/mod/main.go
file 8fec32f skills/x/mod/gitio.go
delete path/to/old.go
patch /tmp/hunks.patch
step [checker] [test] add commitkind tests
file - skills/x/mod/classify_test.go
```

Новый файл режется так (см. RULES.md):

```
step [check] [add] add checker types and function signatures
gen - skills/x/mod/check.go
step [check] [logic] implement parseTag
gen - skills/x/mod/check.go keep=parseTag
step [check] [logic] implement runCheck
gen - skills/x/mod/check.go keep=parseTag,runCheck
```

- `base` обязателен; `source` — откуда берётся итоговое состояние (по умолчанию `HEAD`);
  `build` и `branch` необязательны (по умолчанию `go build -o /dev/null ./...` и
  `review/<текущая ветка>`).
- `file REV PATH` кладёт файл или каталог в состоянии коммита `REV`; `-` означает `source`.
  `REV` должен быть коммитом (или тегом/веткой), не хешем blob.
- `gen REV PATH [keep=A,B]` строит Go-файл из состояния `REV`, где реализованы только функции
  из `keep` (имена как в `commitkind funcs`, методы — `Тип.Метод`), остальные заменены заглушками
  `panic("not implemented")`, лишние импорты убраны; без `keep` — чистый скелет, `keep=*` — весь
  файл. Так новый код режется на технический скелет и бизнесовые реализации по функциям.
- `patch F` применяет подготовленный патч в индекс (для отдельных хунков), `delete PATH` удаляет.
- Всё, что относится к шагу, идёт между `step` и следующим `step`. Шагов без `file`/`patch`/`delete`
  быть не может.
- Тема шага — `[фича] [вид] текст`: фича — `[0-9a-z-]`, все коммиты одной фичи идут подряд.
- Инвариант: после последнего шага дерево ветки совпадает с деревом `source`.

## Если что-то заблокировано

Если система прав блокирует вызов, остановись, ничего не обходи и не дроби команду, чтобы
пройти проверку. Сообщи пользователю, какой вызов заблокирован, и что исходная ветка и рабочая
копия не изменены.
