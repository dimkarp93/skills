# Правила коммитов «для ревью»

## Формат темы

`[фича] [вид] <глагол> <что>` — по-английски, коротко:
`[classify] [rename] rename src to source`, `[classify] [logic] implement side.decls`.

- **`[фича]`** — короткое имя фичи, только `[0-9a-z-]` (например `classify`, `git-io`, `verdict`).
  Имя не должно совпадать с названием вида (`add`, `logic` и т.д.). Каждый коммит принадлежит
  ровно одной фиче; служебные вещи (сборка, документы, скрипты) тоже получают свою фичу
  (`build`, `docs`, …).
- **`[вид]`** — один из: `rename move split unite add remove change fmt logic fix test docs chore`.

Если в репозитории есть хуки, правящие сообщение (например добавляющие `[PROJ-123]`), итог будет
`[PROJ-123] [classify] [logic] implement side.decls`. Хуки важнее этого правила:

- сам префикс не пиши и не подделывай;
- никогда не используй `--no-verify`, `-n`, переопределение `core.hooksPath` и т.п.;
- хук отклонил коммит — прочитай вывод, поправь и повтори, но не обходи;
- пара `[фича] [вид]` ищется в теме в любом месте, лишние скобки хука перед ней допустимы
  (у хуков это обычно `[PROJ-123]` с заглавными буквами, а имя фичи строчное).

## Два класса коммитов

**Технические** меняют только интерфейс и структуру, поведение не меняют и логику не
добавляют. **Бизнесовые** несут логику и функциональность и не меняют интерфейс. Смешивать
нельзя: `commitkind check` отклоняет технический коммит с логикой и бизнесовый с изменением
интерфейса.

| Класс | Вид | Что внутри коммита |
|---|---|---|
| технический | `rename` | только переименование объявления **и всех его использований** |
| технический | `move` | только перенос объявления в другой файл/пакет |
| технический | `split` / `unite` | разбить один тип на два / объединить два в один, вместе с обновлением использований |
| технический | `add` / `remove` | добавить/убрать **аргумент** функции вместе со всеми вызовами (в теле новый аргумент не используется); либо **скелет нового кода** — типы, константы, переменные и функции/методы с заглушкой `panic("not implemented")` |
| технический | `change` | смена типов в сигнатуре (параметры, результат) вместе с вызовами |
| технический | `fmt` | форматирование, AST не меняется |
| бизнесовый | `logic` | вся логика и функциональность: реализация тела заглушки, новая функция с телом, ветка, обработка, изменение или удаление логики |
| бизнесовый | `fix` | исправление бага |
| прочее | `test` `docs` `chore` | тесты, документация, прочее |

`add`/`remove`/`change` — только технические виды; любая логика идёт под `[logic]` (или `[fix]`).
В теме технического коммита пиши, что сделано с интерфейсом; в теле сообщения можно кратко
указать, какая логика будет добавлена следующим коммитом и зачем (`git commit -m "[fetch] [add]
add timeout argument to Fetch" -m "Needed for retries: Fetch will honour it in the next commit"`).
Логику в самом коде технического коммита не пиши: новый аргумент остаётся неиспользуемым,
переименованная функция ведёт себя как раньше.

## Фичи, их порядок и порядок функций

- **Фича** — законченная цель изменения (что получает пользователь). Определи фичи по смыслу.
- **Фичи идут строго по очереди:** сначала все коммиты фичи 1, потом все коммиты фичи 2 и так
  далее; коммиты разных фич не перемежаются (`commitkind check` проверяет непрерывность).
  Технические правки (скелеты, смена контрактов, аргументы) не выносятся в общее начало, а
  остаются внутри своей фичи и идут в ней перед логикой.
- **Порядок фич — от простых и независимых к сложным, зависимости раньше зависящих.** Если фиче
  A нужна функция из фичи B, поставь B раньше A; если зависимость циклическая — вынеси общее
  (скелет общих типов и функций) в отдельную раннюю фичу, но не перемежай.
- **Порядок внутри фичи:** технические коммиты (`rename`, `move`, `split`, `unite`, `add`/`remove`,
  `change`, `fmt`), затем `logic`/`fix`, затем `test`, `docs`.
- **Функции внутри фичи — от простых к сложным:** листовые и короткие раньше, вызывающие и
  длинные позже. Порядок даёт `commitkind order файл.go` (вызываемые раньше вызывающих, при
  равенстве — короче раньше).
- Коммиты гранулярны в обоих классах: одно переименование, одно изменение сигнатуры, одна
  единица логики (функция или связная группа хелперов до ~30–60 строк) — один коммит.
  Технические не создаются «впрок»: фича без нужды в интерфейсе их не получает.

## Обзор для пользователя (до плана и в начале отчёта)

Перед тем как строить план, покажи пользователю обзор и получи согласие на фичи, их порядок и
основные функции. Обзор — компактный, даже если фич и функций много:

- **топ-5 самых важных фич** (если и это слишком сложно — топ-3) в порядке выполнения, у каждой
  одна строка: имя-тег, что получает пользователь, 1–3 главные функции, класс работы;
- остальные фичи одной строкой «ещё N мелких: …», без деталей;
- порядок фич и функций «от простых к сложным» и что от чего зависит, если это неочевидно.

Пользователь соглашается или правит фичи/порядок; детальный план (десятки коммитов) он не
согласовывает. Тот же обзор (`commitkind overview A..B`) открывает итоговый отчёт.

## Как резать новый код

- **Новый код режется на скелет и реализации.** Интерфейс и логика не смешиваются и целиком в
  один коммит не кладутся:
  1. технический `[add]` — скелет файла своей фичи: типы, константы, переменные, сигнатуры
     функций и методов с заглушкой `panic("not implemented")`; собирается, но ничего не делает;
  2. по одному `[logic]` на функцию или связную единицу логики — реализация вместо заглушки, в
     порядке от простых к сложным.
  Новый файл сразу целиком допустим, только если он состоит из данных без логики (типы,
  константы, конфиг) или это документ/скрипт вне Go.
- **Как это делается в плане.** `commitkind funcs файл.go` — функции с числом строк, `commitkind
  order файл.go` — порядок от простых к сложным; шаг `gen REV путь keep=A,B` в плане
  `rr-regroup.sh` кладёт файл, где реализованы только перечисленные функции, остальные —
  заглушки, а лишние импорты убраны. Скелет — `gen - путь` (пустой `keep`), полный файл —
  `keep=*` или `file - путь`.
- **Зависимости между фичами и сборка.** Каждый коммит должен собираться. Если функция фичи
  вызывает функцию другой фичи, которой ещё нет, вернись к порядку фич (зависимость раньше) или
  добавь нужный скелет в раннюю фичу; `main` и другие точки входа получают скелет в самой первой
  фиче пакета.
- Правило «<~50 строк — один коммит» решает, нужно ли делить изменение вообще, и к размеру нового
  файла не применяется: сотни строк логики — это много коммитов.
- **Сворачивание:** мелкий последующий коммит той же фичи (правка версии, опечатка, небольшая
  доработка) можно влить в коммит, где это появилось, но только если результат остаётся одного
  класса и не превращается в крупный коммит со смесью интерфейса и логики. Через границу фичи
  не сворачивай.
- **Промежуточные версии файлов:** если файл менялся несколькими коммитами исходной ветки и по
  плану они остаются раздельными, укажи для этого шага `file <rev> путь` с нужным коммитом
  исходной ветки, а в последнем шаге — `file - путь` (итоговое состояние). Инвариант: итоговое
  дерево новой ветки совпадает с деревом исходной.

## Сборка

Каждый коммит должен собираться (`go build -o /dev/null ./...`, чтобы не оставлять бинарь).
Линтеры (`unused`, неиспользуемый новый аргумент и т.п.) между коммитами не важны: промежуточный
код может быть некрасивым. `go vet` и тесты — один раз в конце. Изменение меньше ~50 строк не
дроби — один коммит с подходящим видом (только если оно целиком технического или целиком
бизнесового класса).

## Инструменты (только Go)

`commitkind` (путь даёт `scripts/ensure-commitkind.sh`):

- `commitkind classify [--staged | REV | A..B]` — JSON семантических изменений;
- `commitkind hint [...]` — строки `[вид] текст (файл)` для черновика плана;
- `commitkind funcs файл.go` / `commitkind order файл.go` — функции файла; порядок от простых к
  сложным;
- `commitkind check A..B` — формат `[фича] [вид]`, вид соответствует тому, что меняет коммит,
  фичи идут по очереди без перемежения;
- `commitkind overview A..B [--top=N]` — фичи диапазона по порядку работы и N самых важных.

`hint` на широком диапазоне может показать переименование, совмещённое с другими правками, как
`add`+`remove` одного имени — сопоставь их сам.

Не читай полные диффы, когда хватает `git diff --stat` и `commitkind classify`. Механические
шаги (rename, add/remove аргумента) делай через `gopls rename` / точечный поиск вызовов, а не
пересказом файлов.

## Ограничения

Только Go. Force-push, merge, PR и правки вне задачи не делай — просьба переписать/сделать
коммиты это не разрешает.
